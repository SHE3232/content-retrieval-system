# 1. 项目背景与目标

个人电脑中的学习资料、项目文档、图片和历史记录往往分散在多级目录里。操作系统按文件名搜索可以解决“记得名字”的问题，却很难回答“只记得内容大意”“想找描述某种物体的图片”或“需要把关键词与语义结果综合排序”这类需求。把文件上传到云端能够获得更强的检索能力，但也带来隐私、网络依赖、服务持续性和许可证边界等风险。本项目因此选择离线优先路线：解析、向量化、索引、查询和结果呈现都在本机完成，默认不把用户文件和查询发往远程服务。

项目面向普通桌面用户和需要可审计交付的课程场景，核心目标是实现一个可运行、可解释、可验证的多模态本地内容检索系统。系统统一支持 TXT、PDF、DOCX、JPEG 和 PNG 五种格式，既能执行关键词检索和文本语义检索，也能在单独的非商业研究配置中执行文字搜图；客户端提供索引库管理、过滤、复制路径、打开文件、状态反馈以及高对比度、文本缩放、键盘操作和减少动态效果等无障碍能力。技术目标之外，项目还要求每个模型、运行时和发布归档都有来源、版本与摘要记录，使“能运行”与“能说明为什么可信”同时成立。

八周工作的总原则是先定义验收口径，再逐步增加能力，并让后续阶段复用前一阶段的稳定契约。解析器输出统一内容模型，嵌入器只接收该模型；存储层只接受带空间、维度、模型和来源元数据的向量；检索层不混淆不同向量空间；API 和 Flutter 客户端只通过稳定协议协作。最终交付不是某次开发环境的快照，而是由固定源码提交、锁文件、运行时、模型清单、测试证据、发布说明和 SHA-256 共同描述的候选版本。

第八周把课程目标收束为三个必须同时完成的结果。第一，完成平台候选、公开源码、演示、作品集和配套待办；第二，形成不少于八千字、图文并茂且能够追溯八周产出的结项报告；第三，在保留 Git 历史和原始仓库可恢复性的前提下，输出独立干净工程目录，删除确认无用的代码、变量、函数、缓存与构建残留，只保留运行、构建、测试、合规和维护所需内容。三个结果均以源码提交 {{SOURCE_COMMIT}} 为事实锚点，平台状态和外部门禁按照证据如实标注。

# 2. 需求分析与验收口径

需求分析采用“用户行为、系统约束、证据要求”三层结构。用户行为包括添加目录、等待索引、输入查询、选择检索通道、组合过滤、查看匹配片段、复制路径、打开文件、删除或重建索引。系统约束包括只能在本机回环地址提供 API、不能自动下载模型、不同向量空间不得直接比较、索引更新必须幂等、失败文件不能破坏已成功内容、退出时需要排空任务并安全关闭持久化存储。证据要求则规定每一个结论由测试日志、结构化 JSON、截图或归档清单支撑，不能仅凭叙述把“计划完成”写成“已经通过”。

功能验收覆盖五种格式的摄取和检索闭环。TXT 需要处理 UTF-8 以及带字节序标记的 UTF-16、UTF-32；PDF 和 DOCX 通过本地 Tika 服务提取正文；JPEG 与 PNG 通过 Pillow 校验和规范化后进入图像通道。索引任务必须返回已解析、已索引、未变化、失败、部分成功与陈旧记录清理等统计。搜索请求必须校验查询文本、通道、权重、分页和过滤条件；结果需要按文件聚合，同时保留得分来源、命中片段、MIME、模态和绝对路径等可解释信息。

非功能验收把性能、安全、无障碍和可发布性变成硬门禁。历史核验基线在一万条文本记录、五十次查询下取得检索 P95 {{SEARCH_P95_MS}} ms，低于两千毫秒目标；这些数字只代表对应硬件与历史提交，不被包装成所有机器上的保证。安全上拒绝非回环监听、校验 Tika 与模型摘要、阻止归档路径穿越、排除密钥和用户数据。无障碍上覆盖语义标签、焦点顺序、键盘触发、高对比度、百分之二百文本缩放和减少动态效果。发布上要求归档内含许可证、版本、启动器和运行时，且默认公开包不得包含受限 MobileCLIP 权重。

验收状态必须允许 PASS、FAIL 与 BLOCKED 三种结果。PASS 表示直接证据满足门槛；FAIL 表示已执行但结果不满足；BLOCKED 表示缺少指定环境、凭据或人工参与，当前无法完成直接验证。macOS 实机、GitHub 匿名访问和真实五分钟录屏等外部条件不能通过 Windows 模拟、脚本自报或占位文件代替。采用这种状态模型会让结项材料少一些“全绿”的表面效果，却能让读者清楚区分代码完成度与外部验收完成度。

# 3. 总体架构与技术选型

系统采用 Flutter 客户端、FastAPI 服务、领域服务层和本地基础设施四层架构。Flutter 只负责交互、状态呈现与偏好持久化，通过 HTTP 调用本机 API；FastAPI 负责输入校验、生命周期、健康状态、任务查询和异常到响应的映射；领域层实现解析、分块、嵌入、索引、检索和文件级融合；基础设施层包含 ChromaDB、Apache Tika、Sentence Transformers、可选 MobileCLIP、本地文件系统与模型清单。分层的价值不在于目录好看，而在于测试可以替换外部进程和真实模型，发布脚本也能明确知道必须复制哪些边界组件。

后端选择 Python 3.10，是因为目标依赖在该版本上有稳定的 CPU wheel，并可由 uv 通过锁文件复现。FastAPI 和 Pydantic 提供类型化请求与响应，ChromaDB 提供持久化余弦向量集合，Sentence Transformers 负责多语言文本空间，PyTorch CPU 运行时承载真实模型。Tika 以本地 Java 进程处理 PDF 和 DOCX，避免在 Python 侧维护两套复杂格式解析逻辑。Flutter 使用单一代码库覆盖 Windows、Linux、macOS、Android 和 Web 工程，最终生产候选则分别由目标平台 Release 构建和实机证据决定是否通过。

模型工程采用“清单先行”而不是“目录存在即可信”。每个模型条目都记录模型标识、向量空间标识、维度、相对路径、运行时、来源修订、许可证和摘要。启动器解析清单并验证目标文件或目录的哈希，缺失、摘要不符、维度不符都会在服务启动前失败。文本模型和图文模型位于不同空间：文本块使用三百八十四维的 text-semantic-v1，图像与文字查询使用五百一十二维的 mobileclip-image-text-v1；检索服务只在同一空间内计算相似度，再在排名层进行融合。

发布架构进一步区分公开源码、默认公开二进制与课程研究包。公开源码不依赖未跟踪的本机 MobileCLIP 路径，`uv sync --locked` 可在隔离环境完成；默认二进制只带 Apache-2.0 文本模型，关键词和文本语义可离线运行，图片语义被明确标为不可用；研究包才加入 MobileCLIP 源码与受研究许可证约束的权重，并携带模型卡、许可文本、来源修订和摘要。这种双轨设计把技术能力与再分发权利拆开，避免根目录 Apache-2.0 被误解为覆盖第三方模型条款。

# 4. 八周实施过程与阶段成果

第一周完成问题定义、用户场景、范围边界和总体架构。项目没有一开始就追求“能搜到”，而是先确定五种格式、本地优先、可访问性和证据驱动四条主线，并建立产品原则、设计约束和目录结构。该阶段的成果为后续工作提供统一词汇：文件摄取、统一内容模型、模型清单、检索通道、索引库和发布候选都在文档中获得明确含义，减少了后续接口反复修改。

第二周实现文件发现和解析。解析器注册表按扩展名与 MIME 选择处理器，TXT 处理编码，PDF 与 DOCX 通过 Tika，图片通过 Pillow；所有解析结果映射为统一的数据结构，并保留来源路径、媒体类型、修改时间、正文或图像信息。该阶段还补充异常隔离、批量处理和摄取时序图，使第三周嵌入层不需要理解具体文件格式。

第三周完成多模态嵌入和模型工程。文本按稳定规则分块并进入多语言 Sentence Transformer，图片和文字查询在 MobileCLIP 联合空间中编码；向量统一进行有限值、维度与归一化校验。NQ 冻结子集用于文本检索质量，COCO 冻结子集用于文字搜图质量，同时记录模型大小、延迟、吞吐量和 LiteRT 转换一致性。第三周的关键产出不是一个模型调用示例，而是可由清单和摘要重建的离线模型边界。

第四周把向量能力接入持久化检索。Chroma 按向量空间建立集合，文件身份、分块身份与记录身份采用稳定算法；重复摄取会识别未变化文件，内容变化会替换旧记录，删除文件会清理陈旧向量。关键词通道采用字段加权 BM25，语义通道分别查询文本与图文集合，再由加权倒数排名进行文件级融合。FastAPI 提供摄取任务、索引任务、搜索、统计、健康状态和优雅关闭接口，形成可被客户端真实调用的本地服务。

第五周完成 Flutter 客户端和无障碍专项。搜索页覆盖空状态、加载、就绪、离线与错误状态；索引库支持查看、重建和删除；设置页持久化后端地址、高对比度、文本缩放与减少动态效果。组件增加语义标签、提示、键盘焦点和 Enter/Space 激活路径，并通过 Windows、Web、Linux、Android 的构建或证据门禁分别记录状态。五格式端到端夹具在真实后端中完成解析、索引、搜索、重建和删除闭环。

第六周聚焦集成、性能、稳定性与发布。启动器负责 Python、Java、Tika、模型、端口和数据目录预检；一键入口负责启动后台服务、等待健康状态并打开前端；打包脚本复制源码、运行时、模型和许可证，再执行轻量化裁剪、路径安全检查和归档体积门禁。压力、故障注入、离线恢复、性能基线、开源合规和五格式回归被组织为可重复执行的门禁，而不是结项前临时截图。

第七周侧重文档、演示材料和验收对账。架构、API、维护、MVP、每周说明、演示脚本和证据索引被统一整理；九段式五分钟演示脚本明确每一段要展示的状态、查询和无障碍操作。此阶段还对外部门禁进行诚实审计：缺少真实参与者、真实 macOS 主机或公开远程仓库时保持 BLOCKED，避免历史文档中的计划性结论污染最终报告。

第八周完成代码清理、公开依赖解耦、平台发布管线和结项材料。通过 Git 跟踪文件白名单、引用搜索、Vulture、测试和真实启动验证识别无用内容；删除已确认未使用的导入、历史临时目录与生成物，并把受限模型、缓存和本机源码副本排除在公开工程之外。Windows 使用 Temurin jlink、Flutter Release 和两类模型暂存生成公开包与研究包；Linux 使用官方 Flutter SDK 和 Temurin 运行时在 Ubuntu 24.04 构建；macOS 提供只允许真实 Darwin 主机和 VoiceOver 证据通过的脚本。最终状态由 {{TEST_SUMMARY}} 以及平台证据共同决定。

# 5. 文件解析与统一内容模型

解析层的第一项设计决定是把“文件发现”和“内容提取”分离。发现器遍历用户选择的根目录，规范化绝对路径，过滤不支持的扩展名，并把每个候选文件交给解析器注册表。注册表依据后缀和媒体类型选择 TXT、Tika 或图像解析器，避免在主流程中堆叠条件分支。解析器返回统一 ParseResult：成功时包含一个或多个标准化文档对象，失败时包含结构化原因和阶段信息，批处理器因此可以继续处理其他文件并给出精确失败清单。

TXT 解析需要面对的主要问题不是读取 API，而是编码不确定性。实现先识别 UTF-8 BOM 以及 UTF-16、UTF-32 的字节序标记，再按受控顺序尝试解码；无 BOM 且无法安全解释的内容会失败关闭，不用替换字符掩盖损坏。换行被规范化但正文语义不被改写，空文件和只有空白的文件获得明确结果。PDF 与 DOCX 通过本地 Tika HTTP 接口提取文本，客户端配置连接与读取超时，并把服务不可用、格式错误和空正文区分开。

JPEG 和 PNG 首先由 Pillow 完成格式校验、尺寸读取和颜色模式规范化。解析结果不把原始图片字节塞进通用文本字段，而是保留图像来源和可由嵌入器安全打开的路径。WebP 虽然在 Flutter 某个筛选文案中曾被列入图片 MIME，但后端解析器没有注册 WebP；最终 README 明确以后端注册表为准，避免界面提示变成错误的功能承诺。该差异被记录为已知限制，而不是通过放宽测试来掩盖。

统一内容模型使下游逻辑只关心模态、来源和可索引内容。文本对象保留文件级元数据以及分块后需要的字符范围，图像对象保留文件元数据与图像尺寸。模型还包含稳定来源标识、MIME、修改时间、文件大小和可选标题，检索结果可以在不重新解析原文件的情况下显示路径、类型与片段。所有路径在进入存储前规范化，Windows 大小写差异和目录分隔符差异不会制造两份逻辑文件。

# 6. 多模态嵌入与模型工程

文本嵌入先把长正文切成具有重叠的稳定分块。分块器按段落和句子边界优先切分，在超长片段上执行确定性回退，并记录每块的序号、字符起止和来源文件。相同内容在相同配置下产生相同分块身份，索引更新才能准确比较新旧记录。Sentence Transformer 以批量方式运行，输出三百八十四维向量；适配器验证形状、有限值和归一化，任何 NaN、无穷或维度漂移都会阻止错误向量进入存储。

图文语义使用 MobileCLIP-S0。图片经过上游提供的预处理管线，文字查询使用同一模型的 tokenizer 和文本编码器，两者进入五百一十二维共享空间。适配器在 CPU 上运行并对查询向量使用受限 LRU 缓存，减少重复查询开销。MobileCLIP 源码固定到上游提交 aecfb5453d022e9deff12f81a150ea8f35194baa，代码采用 MIT；预训练权重固定来源修订并受 Apple Machine Learning Research Model License 约束，因此只出现在课程研究包。

公开版的难点是不能把“删掉权重”误当成完整降级。若基础依赖锁仍引用未跟踪的 MobileCLIP 本机目录，公开源码在另一台机器执行 uv 就会失败；若默认搜索仍请求图片通道，服务则会在运行时崩溃。第八周移除了后端和模型工具基础依赖中的本机路径，把 MobileCLIP 改为研究配置显式安装；运行时从只含文本模型的清单构造不可用图像引擎，默认搜索省略图片通道，显式图片语义请求返回受控能力错误。这样公开版不是残缺包，而是边界明确的文本检索产品。

模型清单承担可复现和合规双重职责。下载工具固定来源修订，下载后离线加载一次并计算目录或文件 SHA-256；启动器再次核对模型标识、空间、维度、路径、许可证和摘要。公开模型暂存器只复制许可允许的文本模型以及清单所引用文件，不复制 `.cache`；研究暂存器在加入 MobileCLIP 时同时要求研究许可证、模型卡和摘要。发布验证器检查归档内部成员，阻止受限权重落入默认包。

历史质量证据显示，NQ 冻结子集四十条查询、五千四百四十六条语料上取得 Recall@10 0.5958；COCO 冻结子集四十张图片、二百零一条标题查询上取得 Recall@1 0.9104。由于子集规模有限，这些数字用于回归与链路验证，不代表面向所有语料的通用准确率。报告保留数据集、样本量、模型空间与硬件条件，避免只展示一个百分比而丢失解释边界。

# 7. 向量存储、索引一致性与生命周期

ChromaDB 按向量空间维护独立的持久化集合。文本语义记录和图文语义记录具有不同维度与模型来源，系统不允许它们进入同一集合或直接计算相似度。记录元数据包含文件身份、分块身份、模态、路径、MIME、修改时间、模型标识、空间标识与维度；存储适配器在写入和读取时都校验这些契约。集合名称和数据目录由配置确定，测试可以使用临时目录，不会污染真实索引。

索引一致性依赖稳定身份和分阶段提交。文件身份来自规范化路径，内容版本结合文件元数据与摘要；文本块身份由文件身份、内容版本和分块序号构造。任务开始时先读取现有文件状态，未变化的文件直接计数并跳过；变化文件完成解析与全部嵌入后才替换旧记录；不存在的旧文件或减少的旧分块在成功提交后清理。若中途解析、Tika、模型或存储失败，失败项被记录，其他文件可继续，原有成功索引不会被半成品覆盖。

生命周期管理由 FastAPI lifespan 统一组装。生产入口加载模型清单、文本嵌入、可选图像嵌入、Chroma 存储、检索服务和任务服务；测试入口可注入内存实现或假嵌入器。关闭阶段先停止接收新任务，再等待进行中的索引任务，最后释放 Chroma 和外部服务资源。启动器只停止自己创建的 Tika 进程，不会误杀用户原先运行的健康服务，这一点通过端口探测和进程所有权记录实现。

索引库 API 提供文件列表、统计、单文件删除和重建。删除操作按规范化身份移除文本与图像空间记录，重建操作复用同一摄取流程而不是复制另一套逻辑。任务状态保存在进程内存，因此服务重启后不能继续用旧任务 ID 查询进度；持久化向量本身不受影响。该限制在 README 和维护文档中明确记录，后续可通过持久化任务表改进，但当前版本不虚构跨重启任务恢复能力。

# 8. 关键词、语义与混合检索

关键词通道采用 BM25，并对文件名、标题和正文设置不同权重。它适合精确术语、编号、文件名片段和短语；文本语义通道适合查询与原文措辞不同但含义接近的情况；图文语义通道则在研究配置中把自然语言查询映射到图片空间。每个通道独立产生有序结果，检索服务不会把 BM25 原始分数与余弦相似度直接相加，因为两种分数的量纲和分布不同。

融合使用加权倒数排名。对于每个通道，结果贡献由通道权重除以常数与排名之和计算；同一文件的多个文本块先保留最有代表性的命中和来源，再在文件级累加贡献。该方法对不同分数尺度更稳健，也允许用户通过权重表达“更相信关键词”或“更相信语义”。响应中保留各通道排名和融合信息，调试错误排序时可以追溯来源，而不是只得到一个无法解释的总分。

过滤在候选生成与结果聚合之间保持一致。请求可限制文本或图片模态、MIME 类型、规范化路径前缀和修改时间范围；分页参数和 top-k 有严格边界。空查询、全空白查询、重复通道、负权重、全部权重为零以及不合法时间范围会在 Pydantic 校验阶段被拒绝。默认公开版若清单中没有图像模型，默认通道集合只包含关键词和文本语义；用户显式请求 image_semantic 时得到能力不可用响应，不会静默把它替换成文本检索。

检索质量和性能分别验证。NQ 与 COCO 冻结子集用于可重复排名指标，一万条合成但结构真实的文本记录用于持久化查询性能；五格式夹具用于验证用户可见闭环。历史 Chroma 链路在四十条 NQ 查询上 P50 为 190.96 ms、P95 为 239.29 ms，四十张 COCO 图片集合的二百零一条查询 P95 为 42.91 ms。最终报告只把这些值标为历史核验基线，不把未重新测量的平台写成相同结果。

# 9. Flutter 客户端与交互设计

Flutter 客户端围绕搜索、索引库和设置三个主任务组织。搜索页顶部提供查询框、搜索触发和过滤入口，中部根据状态展示引导、加载、结果、离线或错误内容；结果卡显示文件名、类型、路径、片段和命中信息，并提供复制路径与打开文件操作。索引库页展示统计和文件列表，允许添加目录、刷新、重建和删除。设置页管理后端地址、主题与可访问性偏好，并在重启后恢复。

状态管理把 API 调用、业务状态与控件拆开。HTTP 客户端负责请求序列化、超时和错误映射；控制器维护查询条件、索引进度和设置；页面只根据不可变视图状态渲染。离线不是一个模糊的异常字符串，而是明确状态：健康检查失败时显示原因和重试入口，后端恢复后可以重新连接而不重启客户端。索引任务通过轮询显示阶段和计数，失败项可查看，而成功内容仍然可检索。

交互设计强调可预测和可恢复。删除索引前需要确认，长路径可以复制，空状态告诉用户下一步动作；过滤对话框按模态、类型、路径和时间组织，关闭后保留选择并能清除。设置保存发生在用户确认之后，失败时不把界面状态伪装成已持久化。设计系统限制颜色和动效依赖，焦点、边框、文字和语义共同表达状态，避免只有颜色差异。

跨平台工程并不等于所有平台已经验收。Windows 是当前主开发和发布平台；Linux 通过 Ubuntu 24.04 与官方 Flutter Linux SDK 构建；macOS 必须在真实 Darwin 主机执行 Flutter Release、后端测试、五格式流程和 VoiceOver 检查。Android 与 Web 保留工程和历史构建证据，但第八周桌面发布清单只对 Windows、Linux、macOS 分别给出直接状态。报告不把“存在平台目录”写成“生产候选已验证”。

# 10. 无障碍设计与验证

无障碍从组件契约开始，而不是发布前附加。交互控件具有明确语义标签和提示，图标按钮不会只依赖图形含义；搜索结果卡的语义顺序与视觉顺序一致；键盘 Tab 顺序覆盖主导航、查询、过滤、结果操作和设置，Enter 或 Space 能触发等价动作。焦点指示具有足够边界，不通过去除系统焦点样式换取“简洁”外观。

视觉适配包括高对比度、文本缩放和减少动态效果。高对比度模式使用明确前景、背景和边框，不把灰色弱对比文字作为关键信息；文本缩放在百分之一百五十和百分之二百下允许布局换行和滚动，不固定卡片高度截断文字；减少动态效果会缩短或取消非必要过渡，同时保留状态变化的可理解反馈。偏好写入本地设置并在重启后恢复，自动化组件测试覆盖持久化和关键布局。

验证证据分为自动化、平台辅助技术和人工可用性三类。自动化测试检查语义树、焦点、文本缩放和设置；Windows 截图与键盘记录覆盖高对比度和焦点路径；Web 的 WAVE 多状态证据覆盖搜索、过滤、索引库和设置。NVDA、VoiceOver、Android Accessibility Scanner 和三名真实参与者测试需要相应环境与人员，未满足时保持 BLOCKED。把自动化通过写成“辅助技术已完全通过”会扩大证据范围，因此最终状态按工具和平台分别描述。

无障碍还影响错误设计。离线、索引失败和无结果状态都使用可读标题、说明与操作，不依赖短暂 snackbar；加载状态既有视觉进度也有语义更新；复制路径等成功反馈不会抢走当前焦点。打开文件调用平台能力前先确认路径存在，失败时返回可理解信息。上述设计使系统不仅在理想搜索结果下可用，也能在网络、本地服务或文件状态异常时维持清晰操作路径。

# 12. 本地数据安全、隐私与开源合规

本地优先不等于天然安全。服务没有身份认证与授权，因此启动器强制绑定 127.0.0.1，并在文档中禁止直接暴露到其他主机。用户选择的数据目录、Chroma 数据、查询和索引任务留在本机；运行时不自动下载模型，也不把查询发送到模型服务。路径输入经过规范化，归档读取与写入拒绝绝对路径、父目录跳转、符号链接和重解析点，临时目录与目标目录必须位于受控父目录下。

供应链控制覆盖 Python、Flutter、Java、Tika 和模型。Python 与 Dart 使用锁文件；Temurin 下载物核对官方 SHA-256，jlink 输出保留 Eclipse Adoptium 元数据；Tika JAR 与官方 SHA-512 配对；模型条目固定来源修订并核对摘要。发布脚本检查 Git 工作树干净且 SOURCE_COMMIT 与 HEAD 完全一致，归档内 PACKAGE_MANIFEST 再记录提交。顶层 DELIVERY_MANIFEST 对每个产物计算字节数和 SHA-256，最终 SHA256SUMS 只从真实文件生成。

开源合规以“项目许可证不覆盖第三方”为前提。项目自有代码与文档采用 Apache-2.0，根目录保留 LICENSE、NOTICE 和 THIRD_PARTY_NOTICES；依赖清单记录包名、版本、许可证和来源。MobileCLIP 源代码采用 MIT，但预训练权重只允许许可证规定的非商业研究用途；COCO 图片按逐图许可处理，NQ 原始与处理数据不进入公开源码。默认公开包排除受限权重、数据集二进制、用户文件、Oracle JDK、CUDA/NVIDIA 包和缓存。

# 14. 关键问题、解决过程与工程反思

第一个关键问题是不同向量空间的边界。早期如果把文本和图片向量视为同类数据，就可能发生维度冲突、错误余弦比较或融合分数失真。解决方案是在模型清单、向量元数据、集合名称和检索通道四处同时携带 space_id，并让存储与运行时双向校验。混合检索只融合排名，不融合原始向量或原始分数。这个问题说明类型和元数据不是文档装饰，而是防止算法错误进入持久化数据的机制。

第二个问题是增量索引的一致性。直接“先删除旧数据再写新数据”在解析或嵌入失败时会让用户失去原有可检索内容。项目改为先完成新版本处理，再按文件身份替换并清理陈旧记录；失败项记录原因，不提交半成品。稳定内容身份和明确任务统计使重复执行可验证。这个过程也形成工程经验：面向本地文件的系统同样需要事务思维，即便底层不是传统关系数据库。

第三个问题是公开发行与研究能力冲突。仅删除 MobileCLIP 权重仍会让锁文件依赖未跟踪源码，公开项目无法安装；删除依赖又可能让默认运行时在导入时崩溃。最终方案将研究依赖从基础锁中移出，使用延迟导入和不可用引擎表达能力差异，默认查询动态选择通道，研究包继续用显式来源恢复完整能力。许可证要求由此成为架构输入，而不是发布结束后的法律备注。

第四个问题是跨平台构建不能依靠“工程存在”。Windows Flutter SDK 在 WSL 中因脚本换行与平台工具链差异不能代表 Linux SDK，项目因此下载并校验官方 Linux Flutter stable；Java 统一采用 Temurin 并以 jlink 裁剪模块；macOS 脚本强制检查 `uname -s` 为 Darwin、拒绝模拟器证据并要求 VoiceOver 记录。把环境真实性写进脚本，比在报告中描述“理论支持”更可靠。

第五个问题是工具行为的非显然细节。PowerShell 父脚本在调用另一个 `.ps1` 后读取 `$LASTEXITCODE`，可能读到子脚本内部 robocopy 留下的可接受非零值，从而把成功打包误判为失败；修复后只依赖 PowerShell 终止错误传播，并加入回归测试。Python 3.10 没有标准库 `tomllib`，测试需要回退到 `tomli`。`uv sync` 下载大型 wheel 可能超过默认三十秒，需要保留缓存并提高 HTTP 超时。这些经验均被写入测试或维护记忆，而不是只解决一次。

清理工程时最大的反思是“少”不等于“删得多”。FastAPI 路由和 Pydantic 校验器由装饰器引用，静态工具可能报告未调用；打包、合规和转换脚本虽然不在常规启动路径，却是可发布与可维护性的关键。项目采用引用搜索、静态分析、测试、运行验证和人工分类五步法，删除有证据的死内容，保留必要注释与受审豁免。干净工程的定义因此是边界清楚、可重建、无无主产物，而不是只剩下一个难以维护的最小程序。

# 15. 最终交付、局限与后续规划

最终交付目录以统一清单组织平台发布、公开源码、课程演示研究包、演示视频、项目作品集和结项文档。SOURCE_VERSION.txt 保存同一四十位源码提交，RELEASE_NOTES 说明能力与限制，DELIVERY_MANIFEST 记录每个产物的相对路径、字节数、SHA-256、发行类别和来源，SHA256SUMS 提供独立校验入口。公开源码由白名单复制 Git 跟踪文件并生成逐文件哈希清单，交付者可以确认没有混入原工作区的缓存和历史构建物。

当前版本仍有明确局限。后端只适合本机单用户回环访问，没有认证、授权和多租户隔离；任务状态不跨进程重启持久化；WebP 后端解析尚未实现；文本和图像检索质量只在有限冻结子集上验证；公开默认包不提供图片语义；模型体积使完全自包含包仍然较大；Windows 和 Linux 的发布证据不能代替 macOS 实机与 VoiceOver。GitHub 发布需要远程仓库和账号权限，真实五分钟视频需要人工按脚本操作并录制声音，这些门禁若无直接证据必须保持 BLOCKED。

后续规划分为三个层次。近期可实现 WebP 解析、持久化任务记录、索引进度事件推送和更细的错误恢复；中期可评估许可证更宽松的图文模型、模型量化、增量模型缓存和跨平台安装器；长期可在仍然保护本地数据的前提下增加可选加密索引、可插拔解析沙箱、可解释相关性反馈和更大规模真实用户评测。所有扩展都应继续遵循空间隔离、清单校验、离线默认和证据驱动原则。

项目八周的主要成果不是把若干技术组件拼接起来，而是建立从需求、架构、实现、测试、许可证到发布的闭环。解析器、模型、存储、检索、API 和客户端各有清晰契约；公开与研究材料各有清晰边界；通过与阻塞各有清晰证据。即使外部门禁尚未全部满足，交付材料也能准确说明已经完成什么、如何验证、哪些仍需在指定环境执行。这样的可审计性是本地内容检索系统能够被继续维护和复现的基础。
