# 架构深度说明

本文解释当前代码的运行边界、模块职责、数据身份、关键流程和设计取舍。字段级 HTTP 契约见
[API 参考](API_REFERENCE.md)，部署、备份、扩展和排障步骤见[维护指南](MAINTENANCE_GUIDE.md)。

## 1. 要解决的问题

用户记得内容、概念或图像，但常常不记得文件名和路径。系统需要在不上传私人文件的前提下，
把异构本地资料转成可检索记录，并同时支持精确词项、文档语义和图文语义检索。

这带来四个直接约束：

1. 推理、索引和存储必须在本地完成，启动阶段就应拒绝缺失或摘要不匹配的模型。
2. PDF、DOCX、文本和图片必须转换成统一记录，但仍保留页码或段落等来源定位。
3. 文本向量和图像向量处于不同空间，不能误混或直接比较。
4. 索引更新后，持久化向量库与进程内关键词目录必须保持同一视图。

## 2. 系统上下文与信任边界

```text
┌────────────────────────────── 用户设备 ──────────────────────────────┐
│                                                                      │
│  ┌──────────────┐    JSON/HTTP on 127.0.0.1    ┌─────────────────┐  │
│  │ Flutter 客户端│ ───────────────────────────▶ │ FastAPI 应用      │  │
│  └──────────────┘                               └────────┬────────┘  │
│                                                        │            │
│                              ┌─────────────────────────┼─────────┐  │
│                              ▼                         ▼         ▼  │
│                       本地文件系统                 本地模型     Tika │
│                    TXT/PDF/DOCX/JPEG/PNG      text/MobileCLIP  :9998│
│                              │                         │            │
│                              └────────────┬────────────┘            │
│                                           ▼                         │
│                                     Chroma 持久化索引                │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

API 没有认证、会话或租户隔离。安全边界是本机进程和回环地址：`tools/start-mvp.ps1` 固定使用
`127.0.0.1`。`authorized_roots` 是每次摄取或索引请求携带的路径约束，服务会解析真实路径并拒绝
越界文件；它不能替代对 API 调用者的身份认证。把该 API 暴露到局域网或公网会让远程调用者提交
本机路径，因此不在当前架构的安全范围内。

## 3. 模块分层

| 层 | 主要目录 | 职责 |
|---|---|---|
| 客户端 | `frontend/lib/` | 用户交互、API 序列化、状态轮询、设置持久化、平台能力和无障碍 |
| HTTP 适配 | `backend/src/content_retrieval/api/` | FastAPI 路由、Pydantic 校验、稳定错误响应、依赖注入 |
| 应用服务 | `services/`、`retrieval/` | 批量摄取、分块、索引编排、文件目录、关键词检索和结果融合 |
| 领域契约 | `domain/` | 解析结果、分块、向量、索引记录、搜索请求/结果和错误语义 |
| 基础设施 | `parsers/`、`embeddings/`、`storage/` | 文件解码、模型适配、模型清单校验、Chroma 持久化 |
| 运行时 | `runtime.py`、`mvp.py` | 本地依赖组装、就绪检查、生命周期和安全关闭 |
| 运维工具 | `tools/`、`model-tools/`、`conversion-tools/` | 启动、烟测、评测、证据校验、转换和交付打包 |

依赖方向总体从 HTTP 和应用服务指向领域契约，再指向通过构造函数注入的基础设施实例。测试使用
假服务替换索引、检索或存储，从而在没有真实模型时验证 API 契约。

## 4. 运行时组装与生命周期

`build_local_runtime()` 是完整后端的组合根，按以下顺序创建对象：

```text
ModelManifest.load + SHA-256 verify
        │
        ├── SentenceTransformerBackend ─▶ TextEmbeddingEngine
        ├── LocalMobileClipBackend ─────▶ MobileClipEmbeddingEngine
        │                                      │
        ├── ParserRegistry + TikaClient         │
        ├── TextChunker                         │
        │           └──────────────┬────────────┘
        │                          ▼
        │              MultimodalEmbeddingService
        │
        └── ChromaVectorRepository
                    ├── IndexingService
                    └── RetrievalService + volatile KeywordIndex
```

运行时只接受经过清单校验的本地模型。固定运行时模型 ID 是 `text-multilingual-v1` 和
`mobileclip-s0-v1`；维度和路径取自 `models/model-manifest.json`。示例清单当前分别使用 384 维
`text-semantic-v1` 与 512 维 `mobileclip-image-text-v1`。

`create_mvp_app()` 在 FastAPI lifespan 启动阶段完成以下工作：

1. 构建本地运行时。
2. 请求 Tika `/version`，要求 200 且正文包含 `Apache Tika`。
3. 把索引、目录和检索服务安装到 `application.state`。
4. 将应用标记为 ready。

`/health/ready` 不只读取布尔标记，还会再次检查 Tika，并调用 Chroma `count()` 验证存储可读。
关闭时，应用先等待所有后台索引任务结束，再关闭 Chroma。30 秒只是告警阈值，不是取消阈值；
达到阈值后仍继续排空任务，以避免索引写入过程中关闭存储。

## 5. 数据身份模型

系统使用多个 SHA-256 标识，每个标识回答不同问题。

| 标识 | 生成方式 | 稳定范围 | 用途 |
|---|---|---|---|
| `file_id` | 文件内容字节 SHA-256 | 内容不变则稳定，与路径无关 | 内容去重、关联同一文件的记录 |
| `source_key` | 规范化绝对路径 SHA-256 | 路径不变则稳定，与内容无关 | 文件级目录、删除和重建 |
| `chunk_id` | 文件 ID、文本、顺序、定位和分片号的规范 JSON SHA-256 | 分块策略和内容不变则稳定 | 文本记录/向量身份 |
| 图片 `source_id` | 等于图片 `file_id` | 图片内容不变则稳定 | 图片记录/向量身份 |
| `record_id` | 等于 `source_id` | 与对应文本块或图片一致 | Chroma 记录 ID |

这套设计让“同一路径内容已变化”和“相同内容位于不同路径”可以分开判断。批量解析会在单次请求
内按 `file_id` 跳过重复内容。持久化目录按 `source_key` 分组，所以文件移动会产生新的来源；旧路径
记录不会因移动自动删除，需要通过文件目录 API 删除或执行维护清理。

## 6. 摄取与解析流程

摄取端点只解析，不写入索引，主要用于检查文件兼容性和解析元数据。

```text
paths + authorized_roots
          │
          ▼
解析并规范化路径 ──越界/缺失──▶ per-file error
          │
          ▼
展开目录、稳定排序、请求内路径去重
          │
          ▼
扩展名路由 ──目录中的不支持文件──▶ skip
          │      └─显式不支持文件──▶ error
          ▼
100 MiB 大小门禁、内容 SHA-256、请求内内容去重
          │
          ▼
TXT / PDF / DOCX(Tika) / JPEG/PNG ParseResult
```

默认单文件上限为 `100 * 1024 * 1024` 字节。TXT 使用确定性编码规则；PDF 保留逐页文本；DOCX
通过本地 Tika 提取正文和少量安全元数据；图片完整解码并验证格式，只保留尺寸、颜色模式及受控
EXIF 字段。异常被转换成每文件错误，批次不会因一个坏文件整体中止。

## 7. 索引流程

索引任务返回 `202` 后在当前 FastAPI 进程内运行。同步 CPU/文件工作通过 `asyncio.to_thread()`
移出事件循环，任务状态存入加锁的内存字典。

```text
解析结果
   │
   ├── 文本/文档 ─▶ 按页或段落分块 ─▶ 文本模型 ─▶ text space records
   │                    1000 字符窗口
   │                    100 字符重叠
   │
   └── 图片 ───────────────────────▶ MobileCLIP ─▶ image-text space record
                                                        │
                                                        ▼
                                              Chroma upsert by space_id
                                                        │
                                      成功且非 partial 时删除旧记录
                                                        │
                                                        ▼
                                              重建进程内 KeywordIndex
```

PDF 的分块定位是 1 起始页码；其他文本按空行分段并保留 1 起始段落号。空文档或缺少 PDF
`metadata.page_texts` 会产生 `CHUNKING_ERROR`。嵌入引擎使用批处理；当一批编码失败时会缩小到
单项重试，以隔离坏输入并产生 `EMBEDDING_ERROR`。

增量判断同时比较内容 ID、预期源记录 ID 集合、模型 ID、空间 ID 和维度。全部一致时计入
`unchanged_files`，不会重新写入。显式重建使用 `force=True`。只有没有局部失败时才删除旧的陈旧
记录，避免部分索引把仍可用的旧分片提前清除。

## 8. 存储结构与缓存

Chroma 数据库位于 `<data_dir>/chroma`。仓库不让 Chroma 调用任何远程嵌入函数，而是显式写入
已归一化向量。每个 `space_id` 对应一个余弦距离 collection，名称是空间 ID SHA-256 的前 24
个十六进制字符并带 `space-` 前缀。

collection 元数据固定记录 `schema_version=1`、`space_id`、`model_id` 和 `dimensions`。打开已有
collection 时若这些值不匹配，写入会失败，而不是把不兼容向量混在一起。

当前有三类内存态：

- 文本查询向量 LRU 缓存，默认 128 项。
- MobileCLIP 文本查询向量 LRU 缓存，默认 128 项。
- Chroma 查询结果 LRU 缓存，默认 16 项。

任何 upsert、删除或清空都会清除 Chroma 查询缓存。关键词索引不持久化，在运行时构造和每次
成功索引变更后从 Chroma 元数据重建。

## 9. 检索与排序

`RetrievalService.search()` 先规范化查询并应用过滤，然后为每个活动通道最多取
`max(20, top_k * 5)` 个候选：

1. `keyword`：进程内 BM25。文件名词项权重重复 3 次，路径重复 2 次，正文重复 1 次；中文按单字
   token，拉丁字母与数字按连续词项。
2. `text_semantic`：把查询编码到文档文本空间并查询对应 Chroma collection。
3. `image_semantic`：把文本查询编码到 MobileCLIP 图文空间并查询图片 collection。

若过滤器只允许图片，文本语义通道会被移除；只允许文本时，图片语义通道会被移除。默认权重为
`keyword=0.35`、`text_semantic=1.0`、`image_semantic=0.85`。

加权 RRF（Reciprocal Rank Fusion，倒数排名融合）先把同一通道内的多个文本块折叠到文件，再按
`weight / (60 + rank)` 汇总。分数以该活动通道集合可达到的第一名总分归一化到 `[0,1]`。最终
结果按分数降序，再按路径和文件 ID 稳定排序；每个文件最多返回一个命中，文本摘要最多 240 字符。

## 10. 并发、一致性与失败语义

所有索引创建、文件删除和文件重建共享一个进程内全局变更锁。同一时刻只允许一个索引变更；
重叠请求返回 `409 INDEX_MUTATION_CONFLICT`。这比按文件并发更保守，但能保证 Chroma 更新和全量
关键词目录刷新之间没有交叉覆盖。

成功写入 Chroma 后若关键词目录刷新失败，服务会清空关键词目录，避免继续提供陈旧关键词结果。
普通索引或重建任务会转为 `failed`；删除端点会返回 503，并明确说明向量记录已经删除但搜索刷新
失败。调用方不能把该 503 当作“删除未发生”。

任务存储只在进程内存在，适合单进程桌面 MVP。多 worker 部署会让不同请求落到不同任务字典，
全局变更锁也无法跨进程协调，因此当前代码不支持 `uvicorn --workers > 1`。

## 11. 前端集成

Flutter 通过 `JsonTransport` 抽象隔离 HTTP，实现和测试可注入假传输。`ContentRetrievalApp` 在启动时
读取设置，然后创建状态、搜索和索引库控制器。设置中的后端地址改变后，旧传输和控制器被关闭，
新服务开始轮询就绪状态。

客户端把索引任务视为 `queued → running → terminal` 状态机。终态是 `completed`、
`completed_with_errors` 或 `failed`。文件打开、路径复制和目录选择位于平台适配层；Web 端没有
本地文件打开能力，跨源访问还需要额外 CORS 配置。

## 12. 设计取舍

### 分离文本和图文向量空间

选择：两个模型、两个 collection、两次语义查询，再在排名层融合。

收益是每种内容使用适合的模型，并通过 `space_id`、模型 ID 和维度校验阻止错误比较。代价是一次
混合查询需要两次编码和两次向量检索，模型包也更大。当前代码没有选择“把所有模态投进一个通用
空间”，因为文本检索质量与图文对齐目标不同。

### Chroma 持久化，BM25 重建

选择：向量和文档元数据持久化，关键词索引在启动和变更后重建。

收益是实现简单，关键词状态可从唯一持久化事实恢复，不需要双写两个数据库。代价是启动时间和每次
索引变更后的刷新成本随记录量增长。当前设计适合桌面级资料库，不适合高频并发写入。

### 进程内后台任务

选择：FastAPI `asyncio` 任务加线程卸载，不引入外部队列。

收益是离线包没有 Redis、数据库队列或守护进程依赖。代价是任务元数据不持久化、不能跨 worker、
进程崩溃后没有恢复。引入持久化任务队列只在需要服务化、多用户或崩溃恢复时才值得。

### 文件级 RRF

选择：通道内先按 `file_id` 折叠，再融合排名。

收益是结果列表不会被同一长文档的多个相邻块占满，用户更快看到不同文件。代价是一个文件内多个
强命中不会累计额外优势，而且响应只返回一个代表性来源定位。

### 保守的全局索引锁

选择：所有索引变更串行化。

收益是一致性规则清晰，删除、重建、批量索引和关键词刷新不会交错。代价是不同目录也不能并行
索引。若以后改为细粒度锁，必须同时解决全量关键词刷新和跨来源 stale record 删除的一致性。

## 13. 扩展点与同步清单

| 要扩展的能力 | 主要改动点 | 必须同步验证 |
|---|---|---|
| 新文件格式 | `parsers/`、`create_default_registry()` | 解析契约、摄取/索引测试、前端 MIME 筛选、本文与 API 文档 |
| 新模型 | 模型清单、`runtime.py`、模型适配器 | 摘要、ID/空间/维度、Chroma 兼容性、准确率与离线门禁 |
| 新检索通道 | `SearchChannel`、`RetrievalService`、`weighted_rrf()` | API schema、权重校验、Flutter 枚举/解析、排序测试 |
| 新持久化 schema | `ChromaVectorRepository.schema_version` | 迁移/重建策略、备份恢复、旧 collection 拒绝行为 |

维护这些变更的具体步骤见[维护指南](MAINTENANCE_GUIDE.md#8-保持代码与文档同步)。
